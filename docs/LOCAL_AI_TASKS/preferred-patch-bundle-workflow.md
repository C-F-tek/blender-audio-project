# Preferred patch bundle workflow

## Purpose

This document records the preferred IA-Carmine patch workflow for future AI-assisted repository work.

The preferred mode is not a monolithic blind patch. It is a controlled, reuse-first patch bundle with modular steps, local application, targeted console fixes when a step anchor fails, explicit validation, and explicit staging.

## Preferred procedure

1. Inspect the repository first.
   - Reuse existing tools, reports, validation scripts, observer files, evidence, manifests, and evidence surfaces before adding new code.
   - Do not duplicate functionality if a reusable tool or report already exists.

2. Generate a modular patch bundle.
   - Use one top-level runner, for example `run_patch_bundle.ps1`.
   - Split the patch into numbered steps under `patches/`.
   - Each step must be independently understandable and mostly idempotent.
   - Prefer targeted file rewrites or robust line/regex insertion over brittle byte-exact anchors.

3. Apply the bundle locally.
   - Run the bundle from the repository root or with an explicit `-RepoRoot`.
   - Let the bundle perform its built-in validation when available.
   - Do not use `git add .`.

4. If a patch step fails, fix the failing step from console.
   - Do not discard the whole bundle immediately.
   - Inspect the actual repository file around the failed anchor.
   - Patch only the failing bundle step or apply a very small targeted fix.
   - Rerun the bundle or the affected validation step.
   - This is the preferred recovery path for script/anchor issues after patch bundle apply.

5. Validate locally before commit.
   - PowerShell parser validation for changed `.ps1` files.
   - `python -m py_compile` for changed Python files.
   - Dedicated smoke tests when present.
   - `git diff --check`.
   - Anti-artifact guard for forbidden paths.

6. Stage explicitly.
   - Stage only intended source/tool/documentation files.
   - Never stage `output/**`, `indexAI/code_chunks/**`, `indexAI/project_code_chunks/**`, `*.db`, `*.sqlite`, `*.sqlite3`, or `renders/**`.
   - Treat generated evidence as review output unless the task explicitly requires a committed evidence file.

7. Record line counts.
   - For every changed script/code file, report the resulting line count.

8. Commit and PR.
   - Commit only after validation passes and the working tree contains no unintended artifacts.
   - Use a focused commit message.
   - Open a PR with validation summary, guardrails, and explicit statement that no forbidden artifacts were committed.

## Preferred recovery pattern

When a bundle fails like this:

```text
[RUN] 02_some_patch_step.ps1
Anchor not found.
Patch step failed.
```

The preferred recovery is:

```text
1. Inspect the target file around the missing anchor.
2. Replace the failing bundle step with a more robust local patch.
3. Rerun the bundle.
4. Validate.
5. Stage explicit file list only.
```

This is preferred over manually redoing the whole patch or weakening validation.

## Current best-practice command shape

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File .\output\validation\patch_bundles\<bundle>\run_patch_bundle.ps1 `
  -RepoRoot C:\Users\carmi\blender\blender-audio-project
```

Then:

```powershell
git diff --check

git diff --name-only |
  Select-String -Pattern '^output/|^indexAI/code_chunks/|^indexAI/project_code_chunks/|^docs/LOCAL_VALIDATION_EVIDENCE/|\.db$|\.sqlite$|\.sqlite3$|^renders/'
```

Then explicit staging only.

## Guardrails

The preferred workflow must not perform implicit destructive actions:

- no merge to `master` unless explicitly requested;
- no force-push;
- no rewrite history;
- no delete/clean of source paths unless explicitly requested;
- no provider execution unless requested;
- no Blender runtime;
- no FFmpeg runtime;
- no patch apply generated by AI without review lane;
- no committing generated output artifacts by accident.

## Classification

This workflow is the default preferred IA-Carmine patch procedure for future repository changes.
